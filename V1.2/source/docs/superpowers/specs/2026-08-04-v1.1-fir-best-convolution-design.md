# V1.1 FIR Best-Convolution Iteration Design

## Goal

Make every V1.1 FIR candidate use the same physical model:

```text
B(n+1) = Constraint(Round(Normalize(Crop(B_best(n) convolution E(n)))))
```

`B_best(0)` is the seven-tap FIR captured from the BERT hardware readback in
the frozen B0 snapshot. `E(n)` is the complete DCA TDECQ Equalizer tap vector
and its reported Main index measured while the latest accepted FIR is active.
The scalar TDECQ value is used only for candidate evaluation and never as FIR
formula input.

The first candidate is therefore `B0 convolution E0`. The former first-pass
shortcut that converted `E0` directly into a FIR is removed from the V1.1
production decision path.

## Scope and non-goals

This change covers the pure FIR formula selection, FIR decision-controller
state, FAKE execution, replay, and hardware-execution adapter behavior needed
to express and test the unified iteration.

It preserves:

- the existing full discrete convolution implementation;
- Main alignment and seven-tap cropping;
- normalization, half-away-from-zero integer rounding, and fixed positive
  Main behavior;
- the FIR L1 limit;
- authorized tap ranges, per-tap steps, and total-change limits;
- frozen Upper/Lower NLC and SSPRQ pattern rules;
- complete BERT write/readback verification, rollback, and
  `RECOVERY_REQUIRED` behavior;
- TDECQ-primary and ER-secondary comparison;
- the existing I2C retune strategy.

This change does not modify sweep persistence, DCA screenshots, frontend code,
Kimi, DINOv2, Bayesian I2C optimization, or the physical hardware drivers. It
does not add a LIVE AI execution factory and must not be represented as a
completed real-hardware AI closed loop.

## Selected approach

Use the existing `calculate_iterative_pass()` implementation for every V1.1
FIR candidate. Keep `calculate_first_pass()` available for compatibility and
its direct unit tests, but remove it from the V1.1 production controller and
FAKE/replay dependency graph.

The public `propose_first()` and `propose_iterative()` entry points and the
persisted `FIRST`/`ITERATIVE` candidate labels remain available. Both entry
points delegate to one private proposal path that:

1. validates the complete Equalizer tap vector and Main index;
2. supplies the controller's current `best_fir.taps` as the left convolution
   operand;
3. supplies the Equalizer taps as the right convolution operand;
4. uses the frozen B0 Main as `manual_main`;
5. validates the resulting target against the FIR model and authorization
   envelope.

This is the smallest compatible change that removes the E-only first pass
without duplicating or altering the established convolution mathematics.

## B0 and baseline measurement

The authoritative B0 comes from the existing explicit Preflight capture. The
BERT `GetConfiguration` response supplies and validates:

- all seven FIR taps in canonical order;
- Upper and Lower NLC;
- BERT port and channel;
- both pattern fields as `SSPRQ`.

No frontend `REFERENCE_FIR`, hard-coded FIR, or GUI-only cache is an allowable
B0 source.

Before optimization candidates, the FAKE/runtime baseline record contains the
B0 TDECQ, Outer ER, Equalizer taps, and Equalizer Main index. The first FIR
proposal reads the Equalizer data while the BERT FIR is still B0. In a future
LIVE AI executor, the same ordering is mandatory: successful BERT readback and
validation, then a DCA measurement at B0, then any candidate write.

## Best-FIR state machine

The controller starts with:

```text
best_fir = B0
best_result = the valid comparison reference
no_improvement_count = 0
```

For each proposal, the convolution base is a snapshot of `best_fir`. A
candidate is never allowed to update this value merely because it was
generated, written, or measured.

An improvement requires a valid TDECQ and the existing confirmation policy.
If the confirmed aggregate is strictly better, the controller updates
`best_fir`, updates `best_result`, resets `no_improvement_count` to zero, and
allows the existing I2C retune stage.

If a candidate is rejected, the controller recommends the unchanged
`best_fir`, increments `no_improvement_count`, and does not request I2C retune.
This rule applies to B1 and all later candidates. A rejected B1 is miss 1; B2
and B3 are calculated again from unchanged B0 and their respective newly read
valid Equalizer vectors. The FIR stage stops only when three consecutive
candidates fail to improve. A later accepted candidate resets the counter.

The `FIRST` and `ITERATIVE` labels remain routing and persistence metadata;
they no longer select different mathematics or rejection rules.

## Invalid Equalizer data

Equalizer taps are invalid when they are missing, not a sequence, have the
wrong count, contain non-numeric or non-finite values, or carry an out-of-range
Main index. A formula result with a zero/non-finite normalization Main or an
illegal seven-tap target is also rejected before candidate creation.

On these failures:

- no `FirCandidate` is produced;
- no candidate `setFir`/apply operation occurs;
- the decision records a specific failure reason and recommends the latest
  valid `best_fir`;
- the active best state is retained; the adapter must not blindly restore B0
  when the best FIR may be newer than B0;
- replay must reproduce the same failure deterministically.

The proposal invariant is that Equalizer taps are read only while the latest
accepted FIR is active. Therefore an invalid tap read normally requires no
write at all. Existing transaction rollback remains responsible for restoring
the last valid state after an actual BERT write/readback failure.

## Execution and replay

The FAKE FIR loop continues requesting candidates after either a FIRST or
ITERATIVE rejection until one candidate is accepted, the controller reaches
three consecutive misses, the candidate budget is exhausted, or a stop is
requested. Rejected targets are restored to the controller-recommended best
before another Equalizer read.

Each persisted FIR observation retains:

- candidate and stage identity;
- formula mode label;
- Equalizer taps and Main index;
- the controller's initial FIR/result;
- raw and aggregate measurements;
- controller decision and no-improvement count;
- requested/applied/readback FIR and full experiment fingerprint.

Replay reconstructs the controller from persisted data and reruns the same
best-FIR convolution decisions in order. It must fail rather than silently
continue if a candidate or decision can no longer be reproduced.

## Hardware-safety boundary

This work is developed and verified only in the isolated feature worktree. No
test may contact DCA, BERT, I2C, VISA, COM, UDP, or invoke a real `setFir`.

The existing BERT transaction remains the owner of complete writes, complete
readback validation, single rollback attempts, and escalation to
`RECOVERY_REQUIRED`. The formula/controller change cannot bypass that layer.

The current repository has a real Preflight readback path and hardware
transaction primitives, but only the FAKE AI execution factory is assembled.
Consequently acceptance proves the algorithm and adapter contract, not an
operational LIVE AI tuning loop.

## Verification

Tests are changed before production code. Required coverage proves:

1. B1 is the exact result of `B0 convolution E0`, not the old E0-only formula.
2. Every later proposal uses the latest accepted `best_fir`.
3. A rejected candidate never becomes a convolution operand.
4. A rejected B1 counts as miss 1 and the stage stops only on miss 3.
5. Invalid Equalizer data produces no candidate and no FIR apply/write.
6. Authorization, Main, L1, per-tap step, and total-change checks still reject
   illegal formula targets.
7. FAKE execution completes at least two FIR candidate iterations and replay
   reproduces their decisions.
8. Existing readback mismatch, rollback, rollback-failure, NLC, and I2C retune
   tests continue to pass.
9. The related focused Python tests and then the complete Python suite pass
   using the isolated worktree source tree.
