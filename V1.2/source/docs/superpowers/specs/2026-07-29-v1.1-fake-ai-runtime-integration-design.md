# V1.1 FAKE AI Runtime Integration Design

## Goal

Connect the existing hardware-independent `optimization/v11` package to the
default persistent V1.1 FAKE runtime through a real cooperative AI execution
factory. A default `create_fake_runtime()` instance must truthfully advertise
`ai_execution_ready: true` only when the complete factory is assembled, and an
`AI_OPTIMIZATION` task must run from HTTP creation through a durable terminal
state without touching physical hardware.

## Scope and non-goals

This integration executes the complete V1.1 sequence:

```text
B0_MEASUREMENT
I2C_COARSE
I2C_FINE
FIR_FIRST
I2C_RETUNE
FIR_ITERATIVE
FINAL_VERIFICATION
RESTORE_B0
```

The runtime adapter calls the existing `CoarsePlanner`,
`DiscreteBayesianFine`, `FirDecisionController`, `RetunePlanner`,
`AlternatingController`, `aggregate_repeated_observations`, and
`compare_results`. It does not copy or restate TDECQ/ER preference, Bayesian
fitting, FIR formula, median aggregation, alternation policy, or the FIR
three-miss convergence rule.

Only FAKE assembly changes. LIVE and READ_ONLY assembly, hardware adapters,
I2C transactions, BERT UDP, `setFir`, and DCA acquisition are out of scope.
The best state remains a persisted recommendation; normal AI execution never
automatically leaves it applied.

## Selected architecture

### Eagerly validated factory

`build_fake_ai_execution_factory(database_path, artifact_root)` loads the
optimizer API through `optimizer_bridge`, verifies the required public
interfaces and numerical dependency, and returns a callable factory only when
the complete FAKE execution graph can be constructed. `runtime.create_runtime`
passes that factory together with `FakeSweepExecutor` to
`PersistentV11TaskRunner`.

Runner readiness remains derived from the presence of a usable injected
factory. The runtime does not hard-code the capability. If optimizer loading or
factory validation fails, the default runtime either fails assembly with a
specific integration error or leaves AI readiness false; it never substitutes
an immediate-success or empty executor.

### Deterministic FAKE plant

`FakeOptimizationPlant` owns only in-memory I2C and FIR state. It starts from
the frozen B0, applies authorized candidates to that in-memory state, returns
exact readback, exposes deterministic synthetic DCA taps, and produces
deterministic `MetricResult` samples. It imports no hardware driver and opens
no device or socket.

The FAKE measurement surface creates TDECQ and ER values; it does not rank
them. All ranking remains in the pure optimizer's `compare_results`, where
TDECQ is primary and ER is only the exact-TDECQ tie-breaker.

### Cooperative persistent execution

`FakeV11AIExecution` implements the runner's existing `run(stop_event)` and
`restore_b0()` protocol. It owns no service-thread SQLite connection. Each run
opens a worker-local `TaskStore`, reads durable observations and best state,
and resumes from those records.

At every candidate boundary the execution performs:

1. reconstruct pure algorithm history from committed observations;
2. ask the current pure controller for exactly one candidate;
3. apply the candidate only to the FAKE plant;
4. measure one result or the existing FIR controller's three-result
   confirmation batch;
5. persist one aggregate candidate observation;
6. update `BestStateRecord` only after the referenced observation commits;
7. atomically refresh the optimization artifact;
8. check the cooperative stop event before requesting another candidate.

No optimizer observes an uncommitted measurement. Resume creates a fresh
execution and replays persisted decisions, so it does not trust an object from
the previous run or process.

## Candidate budget

`candidate_budget` is one global hard upper bound for the entire AI task. B0
does not consume it. I2C coarse, I2C fine, FIR, and retune each consume one unit
per executed candidate. A FIR candidate's first read plus two confirmation
reads are stored as one observation and consume one unit.

The execution derives a deterministic stage plan:

- coarse receives at most one quarter of the global budget, with a minimum of
  two points when the discrete space and budget permit, and an upper bound of
  eight points;
- one FIR and one retune slot are reserved for each allowed alternation round;
- fine receives the remaining pre-FIR budget;
- an exhausted parameter space or an existing controller stop decision ends a
  stage early rather than manufacturing a candidate;
- unused reserved budget is not required to be spent because the budget is a
  maximum, not a target.

The pure planners still decide candidate ordering and convergence within each
stage. The runtime allocation only prevents one stage from consuming the
campaign-wide authorization before later stages can run.

## Durable observation and best-state model

The existing `ObservationRecord` remains the authoritative candidate record.
Each candidate observation stores:

- a deterministic observation and candidate ID;
- stage and alternation round;
- requested, applied, and readback state;
- TDECQ, ER, validity, and aggregate status;
- optimizer model version and reason;
- exact FIR/NLC/DCA experiment fingerprint;
- raw repeated measurements for FIR confirmation;
- the cumulative candidate index used for budget enforcement.

The runtime converts committed records back to `I2CObservation`,
`MetricResult`, `ExperimentFingerprint`, and complete combination objects.
Replaying those objects restores Bayesian training history, actual-readback
features, FIR historical best, FIR no-improvement count, and alternating
stage/round decisions.

`BestStateRecord` is updated only when `compare_results` says a committed
complete I2C+FIR state is strictly better. It contains I2C, seven FIR taps,
NLC, pattern, BERT mapping, DCA fingerprint, and the metric result. It never
claims that this state remains applied.

## Lifecycle and recovery

- Normal completion and no-improvement completion both restore B0 before the
  runner commits the terminal lifecycle.
- Pause and abort are cooperative at candidate boundaries. The execution
  restores B0 before the service records `PAUSED` or `ABORTED`.
- Resume constructs a new execution from SQLite and skips all persisted
  candidate IDs.
- A process restart preserves tasks, observations, events, best state, and
  artifacts. Existing startup recovery marks interrupted work
  `RECOVERY_REQUIRED`; no automatic mutation occurs.
- A candidate or persistence failure attempts one B0 restore. Verified restore
  produces `FAILED`; failed or unverifiable restore produces
  `RECOVERY_REQUIRED` and retains execution authority.
- The existing SQLite active-task invariant, process hardware authority, and
  one-worker/no-queue runner remain the three execution-ownership guards.

## Artifact

The execution atomically refreshes:

```text
artifacts/v1.1/<task_id>/optimization_result.json
```

The artifact contains product/schema/runtime metadata, task/config/B0 hashes,
candidate counts by phase, ordered observation IDs, persisted best state,
terminal lifecycle when available, `best_applied_to_hardware: false`, and the
latest verified B0-restoration status. SQLite remains authoritative.

## Hardware isolation

The FAKE execution module may import pure optimizer models and pure FIR formula
functions, but it may not import or construct PyVISA, pyserial, VD1124/real I2C,
VIT BERT UDP, or DCA acquisition adapters. Acceptance runs install import and
network blockers and assert that no `setFir`, I2C write, VISA/COM connection,
BERT UDP send, or DCA acquisition occurs.

## Verification

Tests are written and observed failing before implementation. Coverage includes
truthful default readiness, full HTTP lifecycle, adaptive Bayesian candidates,
strict objective behavior, the existing three-miss FIR stop, global budget,
observation/candidate equality, complete best state, no implicit apply,
Pause/Resume/Abort, process restart persistence, rollback failure,
single-task ownership, all runtime health endpoints, final report, and artifact
validation. Final acceptance runs the Python suite, frontend suite, lint,
production build, and a fresh-database FAKE Optimization proof.
