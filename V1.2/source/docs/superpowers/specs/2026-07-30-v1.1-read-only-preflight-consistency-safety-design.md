# V1.1 READ_ONLY Preflight Consistency and Safety Design

**Date:** 2026-07-30

**Status:** Approved

## Goal

Repair the V1.1 FAKE campaign regression and make the built-in READ_ONLY
Preflight produce one internally consistent, fully audited hardware capture.
Only an explicit hardware-snapshot request may open query/readback drivers.
Mapping, parameter validation, sweep counting, and B0 freezing must consume the
same immutable capture by `snapshot_token` without reconnecting hardware.

## Scope

This design covers:

- the legacy FAKE campaign `entry_factory` regression;
- V1.1 READ_ONLY capture ownership and token-bound reuse;
- one-session VD1124 identity and parameter readback;
- audited VD1124 page-selection side effects and verified page restoration;
- a complete query-only FlexDCA fingerprint;
- bounded Preflight timing, connection lifecycle, and evidence artifacts;
- backend, API, frontend contract, and regression tests.

It does not enable READ_ONLY task execution, DCA acquisition, I2C tuning
writes, BERT FIR/NLC writes, or History Apply.

## Safety invariants

1. Importing modules, constructing the runtime, starting the API, requesting
   health, and requesting capabilities do not import optional live drivers or
   open VISA, serial, or UDP resources.
2. Only `GET /api/v1.1/hardware/snapshot` may call
   `V11Gateway.preflight_capture()` in READ_ONLY mode.
3. READ_ONLY never sends a DCA command without `?`, never performs Clear,
   Single, Run, Autoscale, or source selection, and never changes a DCA setup.
4. READ_ONLY performs zero VD1124 tunable-register writes. Page-select writes
   required by the STM32 bridge are separately counted and audited.
5. READ_ONLY performs zero `setFir` calls and zero BERT NLC writes.
6. Identity, endpoint, source, units, pattern, page-restore, timeout, or
   response-validation failure prevents creation of both `PreflightCapture`
   and `B0Snapshot`.
7. Every resource opened during Preflight is closed on success, failure, or
   timeout.

## Architecture

### Immutable token-bound capture

`V11ApplicationService.hardware_snapshot()` remains the only operation that
acquires the shared hardware authority and invokes `gateway.preflight_capture()`.
On success it stores one immutable `PreflightCapture` under its
`snapshot_token`.

The service keeps one active capture generation. A later successful hardware
snapshot invalidates prior unfrozen tokens. This avoids unbounded in-memory
growth and prevents an operator from accidentally combining evidence from two
Preflight runs. Unknown, invalidated, or unavailable tokens fail closed.

The following operations require the exact token and only read the stored
capture:

- mapping scan;
- parameter validation;
- sweep point counting;
- B0 freeze.

No one of these operations acquires hardware authority or calls a gateway
method. The service checks that all returned hashes and channel mappings come
from the selected capture.

### API contract

The API uses explicit request objects rather than an implicit "latest
capture":

```json
POST /api/v1.1/mapping/scan
{"snapshot_token": "read-only-snapshot-..."}
```

```json
POST /api/v1.1/parameters/validate
{
  "snapshot_token": "read-only-snapshot-...",
  "parameters": [{"name": "eq", "min": 1, "max": 10, "step": 1}]
}
```

```json
POST /api/v1.1/sweeps/count
{
  "snapshot_token": "read-only-snapshot-...",
  "hardware": "I2C_SWEEP",
  "mode": "FULL_GRID",
  "parameters": [{"name": "eq", "min": 1, "max": 10, "step": 1}],
  "seed": 0,
  "max_points": 10
}
```

`POST /api/v1.1/tasks/{task_id}/b0` already contains `snapshot_token` and keeps
that contract. FAKE uses the same token-bound flow so the frontend and tests do
not require mode-specific behavior.

### Capture evidence

`PreflightCapture` gains immutable evidence with these sections:

- `started_at_utc`, `finished_at_utc`, and `total_duration_s`;
- DCA, I2C, and BERT connection and query durations;
- normalized VISA, COM/baud/address, and UDP/port/channel targets;
- every approved DCA query, raw response, and normalized response;
- VD1124 raw register bytes and decoded field values;
- VD1124 entry page, each page-select event, restore target, restore readback,
  and `restore_verified`;
- BERT raw mode and configuration responses and normalized FIR, NLC, and both
  pattern fields;
- explicit mutation counters.

The mutation summary is shaped as follows:

```json
{
  "dca_configuration_writes": 0,
  "dca_acquisition_commands": 0,
  "i2c_tunable_register_writes": 0,
  "i2c_page_select_writes": 2,
  "bert_fir_writes": 0,
  "bert_nlc_writes": 0
}
```

The service atomically writes successful evidence to
`artifacts/v1.1/preflight/<snapshot_token>.json`. A failed capture writes a
separate failure artifact containing the safe partial audit and error, but it
does not contain a B0, does not create a usable token, and is never inserted
into the capture cache.

## VD1124 one-session readback

The production driver factory opens one serial connection for identity and all
parameter reads. It constructs pyserial without a port, sets `DTR=False` and
`RTS=False`, disables `dsrdtr` and `rtscts`, assigns the reviewed COM port, and
then opens the connection. This prevents the act of opening COM from
implicitly asserting bridge control lines.

The read-only VD1124 session:

1. reads the entry page register;
2. groups identity and parameter reads by page to avoid redundant selects;
3. records every page-select frame and acknowledgement;
4. reads chip ID, revision, raw parameter bytes, and decoded values;
5. restores the entry page in `finally`;
6. reads the page register again after restoration;
7. accepts the result only when restore readback equals the entry page.

If the main read fails and page restoration also fails, the page-restore error
is the safety-critical failure and preserves the original read error as
context. No tunable-register writer is constructed or exposed.

The audit deliberately does not claim zero physical I2C writes: bridge
page-select operations are writes to the page register. It separately attests
that tunable-register writes are zero.

## FlexDCA query-only fingerprint

The allowlist contains only exact, approved queries. The optical channel query
is derived from the configured and verified Outer ER source, then matched
against the resulting exact allowlist entry.

The fingerprint queries are:

- `*IDN?`;
- `:CHANnel{N}{A-D}:WAVelength:VALue?` for the verified optical channel;
- `:TRIGger:SOURce?`;
- `:TRIGger:DCDRatio?`;
- `:TRIGger:SRATe?`;
- `:TRIGger:PLENgth?`;
- Outer ER source, units, status, and details;
- TDECQ source, status, and details.

The fingerprint stores the configured function number, verified Outer ER
channel, verified TDECQ function, wavelength, trigger source, divide ratio,
symbol rate, pattern length, and both measurement status/detail groups. The
BERT capture remains the authority for the textual pattern name (`SSPRQ`) and
must attest `SSPRQ` in both commissioned response fields.

The implementation rejects blank responses, malformed numerics, non-finite
values, and FlexDCA invalid placeholders such as `9.99999E+37`.

## Bounded lifecycle

The profile's characterization measurement timeout is the total Preflight
deadline. Before each device operation the capture computes the remaining
time and caps the device I/O timeout to that value:

- VISA query timeout is capped before each DCA query;
- serial read and write timeouts are capped before each bridge transaction;
- BERT UDP timeout is capped before each request.

The deadline is checked before and after each operation. The driver context
manager owns all opened resources and closes them in reverse order. A timeout
raises `ReadOnlyPreflightError`, discards captured values, and emits only a
failure audit.

## Runtime-mode behavior

The legacy campaign `entry_factory` rejection is conditioned on
`RuntimeMode.READ_ONLY`. FAKE continues to build its deterministic tuning
profile and fake adapters. LIVE_TUNING continues to require both an explicit
hardware adapter factory and a human-approved tuning profile factory at
runtime assembly.

The built-in READ_ONLY runner still rejects every task execution command.

## Testing

### FAKE regression

The existing HTTP E2E test must again complete campaign Preflight and the full
FAKE flow while rejecting imports of real hardware modules.

### Capture consistency

Service and HTTP tests assert that:

- one hardware snapshot makes exactly one gateway capture call;
- mapping, validation, sweep counting, and B0 freeze with that token make no
  additional gateway or driver calls;
- a second snapshot invalidates the first unfrozen token;
- an unknown or invalidated token fails closed.

### VD1124 safety

Serial spies cover:

- one open/close cycle for identity and all fields;
- DTR and RTS deasserted before port open;
- grouped page selection and complete event audit;
- successful restore and restore readback;
- restore mismatch and restore-read failure;
- main-read failure followed by successful restore;
- no tunable-register write API or frame.

### DCA fingerprint

DCA spies assert the exact query order and complete normalized fingerprint.
Every command must be in the allowlist and be a query. Tests fail on any DCA
write, Clear, Single, Run, Autoscale, source selection, malformed response,
source mismatch, invalid status, or invalid numeric placeholder.

### Timeout and cleanup

Deterministic clocks and blocking spies verify per-device timing, total timing,
deadline failures, failure artifact content, absence of partial B0, and closure
of every opened resource.

### Final verification

- focused FAKE E2E;
- focused READ_ONLY and VD1124 tests;
- complete Python suite;
- frontend unit tests;
- TypeScript and Vite production build;
- static review confirming startup/health/capabilities remain connection-free.

No automated verification in this task may use real DCA, I2C, or BERT
endpoints.
