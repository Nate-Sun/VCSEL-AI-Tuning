# VCSEL AI Tuning V1.1 Authorization and API Contract Design

## Purpose

Repair the V1.1 authorization request parser and replace the frontend's temporary V1.1 routes and payloads with the production FastAPI contract. The completed flow must use a fresh FAKE runtime, preserve the existing fail-closed authorization checks, and never contact real hardware.

Development occurs on `codex/v1.1-auth-contract-fix` in the isolated worktree `.worktrees/v1.1-auth-contract-fix`, based on `codex/ai-tuning-v1.1`. After full verification, the feature branch will be merged into `codex/ai-tuning-v1.1`. The validation worktree remains untouched.

## Scope

The change includes:

- strict RFC3339 parsing for `AuthorizeTaskRequest.expires_at`;
- canonical, typed frontend functions for every V1.1 API operation currently exported by the client;
- a Wizard flow that completes read-only pre-task validation before creating a full task document;
- explicit `DRAFT -> B0_FROZEN -> AUTHORIZED -> RUNNING` server-driven state handling;
- a fixed 30-minute authorization window;
- backend, frontend, real-FastAPI integration, browser E2E, and localhost HTTP regression coverage.

The change does not add renewable authorization, a task-runtime limit, a combined authorize/start endpoint, or any hardware implementation. An uninterrupted `RUNNING` task is not stopped when the authorization window expires. An expired authorization cannot be reused to start, resume, or recover execution.

## Backend RFC3339 parsing

`StrictRequest` remains globally strict. `AuthorizeTaskRequest.expires_at` becomes an `Annotated` aware-datetime field with a dedicated `BeforeValidator`.

The validator accepts only a string matching the RFC3339 shape:

```text
YYYY-MM-DDTHH:MM:SS[.fraction](Z|+HH:MM|-HH:MM)
```

It normalizes a terminal `Z` to `+00:00`, parses the string into `datetime`, and returns that value to Pydantic. `AwareDatetime` then remains responsible for the final timezone-awareness validation. The validator rejects naive timestamps, malformed dates or offsets, numeric epochs, Python `datetime` inputs, arrays, objects, booleans, and null. `operator_confirmed` remains `Literal[True]`.

The service continues to generate `issued_at` from the server clock, require `expires_at > issued_at`, re-attest the frozen B0 and hardware evidence, and reject expired authorization at start, resume, and resume-recovery boundaries.

## Canonical frontend API client

`TEMPORARY_V11_ENDPOINTS` is removed. The client exposes named, strongly typed operations whose method, path, body, and response schema match the checked-in backend contract and the FastAPI OpenAPI document.

The Wizard uses these endpoints:

| Operation | Method and path | Body |
|---|---|---|
| Snapshot | `GET /api/v1.1/hardware/snapshot` | none |
| Mapping scan | `POST /api/v1.1/mapping/scan` | none |
| Parameter validation | `POST /api/v1.1/parameters/validate` | bare parameter-selection array |
| Sweep count | `POST /api/v1.1/sweeps/count` | hardware, mode, parameters, seed, max_points |
| Create task | `POST /api/v1.1/tasks` | complete `CreateTaskRequest` |
| Freeze B0 | `POST /api/v1.1/tasks/{task_id}/b0` | snapshot_token and literal confirmation |
| Authorize | `POST /api/v1.1/tasks/{task_id}/authorization` | authorization_id, expires_at, literal confirmation |
| Start | `POST /api/v1.1/tasks/{task_id}/start` | none |

Wire enums are translated explicitly:

- frontend I2C sweep -> `I2C_SWEEP`;
- frontend BERT FIR sweep -> `BERT_FIR_SWEEP`;
- frontend single-parameter mode -> `SINGLE_PARAMETER`;
- frontend full-combination mode -> `FULL_COMBINATION`.

Other exported V1.1 operations are migrated from temporary campaign/operation routes to the documented task routes. This includes task recovery, task observations/results, sweep pagination and downloads, final reports, history apply, and explicit history recovery. Unsupported operation polling is removed instead of being preserved behind a mock-only endpoint.

Response parsing remains strict enough to detect a contract mismatch. A successful HTTP status with an unexpected lifecycle state is treated as a failure and is never converted into an optimistic UI state.

## Wizard data flow

The Wizard no longer creates a task after the first step. It accumulates validated setup evidence first:

1. The operator selects task type and confirms the complete physical channel mapping.
2. The frontend performs the read-only hardware snapshot and stores its `snapshot_token` and returned evidence.
3. The frontend asks the server to scan the Script/RegMap mapping.
4. The operator selects parameters and the frontend sends the exact parameter array for server validation.
5. The operator selects depth/profile; the frontend resolves the server-provided candidate budget and any required advanced iteration limit.
6. For Sweep, the frontend sends the canonical sweep hardware/mode/seed/max-points payload and requires a successful deterministic count.
7. On transition to final review, the frontend generates a task ID and sends one complete `CreateTaskRequest` containing task type, confirmed channel mapping, validated parameters, depth, candidate budget, and all required Sweep fields.
8. Only after task creation succeeds does the frontend freeze B0 with the snapshot token. It requires the returned lifecycle state to be `B0_FROZEN`.
9. The final confirmation page displays the frozen evidence and the exact authorization expiry.

The channel mapping sent to the backend contains an integer `i2c_channel`, explicit `bert_port` and `bert_channel`, fixed TDECQ source `FUNC1`, fixed Outer ER source `CHAN1A`, and literal operator confirmation. The UI does not offer incompatible DCA source choices.

## Confirm and start transaction

One click performs two separate, ordered HTTP requests:

1. Generate a unique authorization ID and an RFC3339 UTC expiry exactly 30 minutes after the click-time clock value.
2. POST authorization.
3. Parse the server response and require `state === "AUTHORIZED"`.
4. Only then POST start with no request body.
5. Parse the start response and require `state === "RUNNING"`.
6. Update navigation and visible state from the returned task document.

An authorization HTTP error, response-schema error, or non-`AUTHORIZED` state terminates the sequence and proves that start was not called. The same fail-closed rule applies to start: the UI shows the server error or unexpected state and does not claim execution began.

The 30-minute value is an authorization start/resume window, not a maximum AI Tuning runtime. The current V1.1 authorization remains immutable and non-renewable.

## Testing strategy

Implementation follows strict RED-GREEN-REFACTOR cycles.

Backend regression tests cover JSON RFC3339 with an offset, terminal `Z`, a naive timestamp, malformed text, numbers and other non-string inputs, and `operator_confirmed: false`. Route/service tests prove `B0_FROZEN -> AUTHORIZED` and `AUTHORIZED -> RUNNING` without weakening expiry or attestation checks.

Frontend unit tests capture `fetch` calls and assert exact HTTP methods, canonical paths, no-body semantics, complete payloads, enum translations, lifecycle response checks, and a 30-minute expiry. A dedicated failure test proves that authorization rejection or an unexpected authorization state never invokes start.

A real integration test uses the production FastAPI application and a new temporary FAKE SQLite database to perform snapshot, mapping scan, validation, task creation, B0 freeze, authorization, and start. It does not use MSW. Browser E2E drives the production frontend against that FAKE server. A final localhost HTTP smoke run records representative request and response bodies for delivery.

The same browser integration continues through the task-scoped V1.1 run page
and validates real capability, active-task, task, event, observation, and Sweep
point responses with the frontend schemas. The generated OpenAPI currently has
anonymous success responses because the route functions return `Any`; this
test is the compatibility evidence until typed FastAPI response models are
introduced. BERT FIR selection remains disabled in the Wizard until FIR tap
parameters are part of the browser mapping contract.

Final acceptance runs:

- the complete Python test suite;
- the complete frontend unit test suite;
- the frontend production build;
- the complete frontend Playwright E2E suite;
- a fresh-database FAKE localhost HTTP flow.

## Safety boundaries

All automation uses FAKE/injected services only. Tests and smoke verification must not open VISA resources, serial or COM ports, or BERT UDP sockets; execute I2C writes; call `setFir`; issue DCA acquisition commands; or import a live hardware service factory. No compatibility route may combine authorization and start or bypass the state machine.

## Delivery and merge

Before commit and merge, the implementation diff is reviewed against every requirement and all verification commands are rerun from the feature worktree. The implementation commit hash, changed files, test counts, real HTTP transcript, and explicit no-hardware statement are reported. The clean integration worktree then merges `codex/v1.1-auth-contract-fix` into `codex/ai-tuning-v1.1`; the merge ancestry and final integration hash are verified afterward.
