# V2.1 Kimi Compact Optimization Memory Design

## Goal

Give stateless Kimi API calls enough experiment history to compare the current
PAM4 eye with the best prior eye while keeping image and text token growth
bounded. The change must not alter V2.0 candidate validation, I2C execution,
readback, DCA measurement, rollback, or recovery behavior.

## Chosen approach

V2 owns the memory. Every successfully parsed Kimi assessment is stored locally
in one campaign-scoped JSONL journal. A request sends only:

- the current eye-density image;
- the current best eye-density image, when one exists;
- compact summaries of the five most recent assessments;
- the current readback, metrics, instruction, and local safe candidates.

Kimi never receives all historical images or a density matrix serialized as
text. The full verified `EyeSample` remains in the local journal so the best
reference image can be reconstructed from its NPY artifact when needed.

## Rejected alternatives

### Full conversation and image history

Resending every historical image makes input cost grow on every sweep point and
eventually exceeds practical context limits. It is unnecessary because the
decision needs the current eye, one stable reference, and a short trajectory.

### Raw density matrix as prompt text

A 751 by 521 matrix contains about 391,000 numeric values. Serializing it as
text is larger and harder for a multimodal model to interpret than the existing
fixed 392 by 280 RGB rendering.

### Database, vector store, or RAG

The first live version has one ordered experiment trajectory per campaign.
JSONL plus deterministic selection is sufficient and easier to audit. No
semantic search is required.

## Components

### `v2/kimi_memory.py`

`KimiMemoryEntry` is a strict immutable record containing:

- the complete `EyeSample` used for the assessment;
- the validated `PerceptionResult` and `DecisionProposal`;
- the UTC record timestamp.

`KimiCampaignMemory` owns one explicitly supplied JSONL path. It:

- validates every line and rejects malformed or cross-campaign history;
- rejects duplicate measurement IDs;
- returns at most the five latest compact summaries;
- derives the current best entry deterministically;
- appends and `fsync`s a new assessment before any selected candidate is sent
  to the hardware execution path.

The journal records the assessment and proposal, not a claim that the proposal
was executed. Hardware execution status remains in `v21_result.json` and the
existing campaign repository. The next `EyeSample.readback_params` is the
source of truth for what was actually applied.

### Comparison provenance

`PerceptionResult` gains two optional fields:

- `reference_measurement_id`;
- `better_than_reference`.

They must either both be absent or both be present. The first assessment has no
reference. Later Kimi assessments identify the exact best measurement shown as
the second image and return a strict boolean comparison.

An assessment is eligible to become the best only when both perception and
decision retain the Kimi provider identity, the eye is valid, and it is not
out-of-distribution. The first eligible assessment becomes the initial best.
A later assessment replaces it only when it compares against that exact best
measurement and `better_than_reference` is true.

### `KimiProvider`

The provider receives a `KimiCampaignMemory`. Before calling the API it loads
the campaign memory, preprocesses the current NPY, preprocesses the best NPY
when available, and passes the five compact summaries to the client. It does
not mutate memory during analysis.

### `KimiApiClient`

The client accepts an optional reference PNG and recent summaries. The user
content clearly labels current and reference images. The strict response schema
adds nullable `better_than_reference`:

- it must be null when no reference image was supplied;
- it must be boolean when a reference image was supplied.

The API key, base64 image data, and full historical journal are never logged or
written to result files.

### `execute_kimi_step`

After `brain.analyze()` returns and before `run_one_candidate()` is called, the
step records the current assessment in `KimiCampaignMemory`. A memory validation
or write failure therefore prevents hardware execution. `HOLD` and `STOP`
assessments are also recorded when they are valid Kimi responses. Provider
errors generated by the outer fail-closed brain are not written as Kimi
assessments.

Before appending a `PROPOSE` assessment, the step preflights the
`v21_result.json` publication directory by creating a unique temporary file,
flushing and `fsync`ing it, and removing it. A preflight failure prevents both
the memory append and hardware execution.

## Data flow

```text
current EyeSample
  -> load campaign JSONL
  -> select best prior EyeSample and five recent summaries
  -> preprocess current NPY and optional best NPY
  -> Kimi strict JSON response
  -> V2.0 brain confidence and candidate validation
  -> preflight v21_result.json directory with temp create/fsync/remove
  -> append validated assessment to JSONL
  -> existing run_one_candidate safety chain
  -> v21_result.json plus existing campaign observations
```

## Failure behavior

- Missing history file means an empty history and is valid for the first point.
- Corrupt JSONL, duplicate IDs, campaign mismatch, missing best artifact, or
  hash mismatch causes provider failure and `HOLD`; no candidate is executed.
- A response with comparison data but no reference, or without comparison data
  when a reference was supplied, is rejected.
- A stale comparison against a measurement other than the derived current best
  is rejected before hardware execution.
- A journal append failure is raised before hardware execution.

## Token bound

Every request contains at most two fixed-size 392 by 280 eye images and five
small JSON summaries. The number of sweep points does not increase request size.
All older NPY, PNG, and JSON artifacts remain local for audit and later model
training.

## Tests

Tests use verified temporary NPY artifacts and a request-recording SDK object;
they do not call the network or hardware. They prove:

- first assessment sends one image and null comparison;
- later assessment sends current plus best images and five summaries at most;
- a better current eye becomes the next reference;
- malformed or cross-campaign history fails closed;
- comparison/reference inconsistencies fail closed;
- memory is written before the orchestrator is called;
- a memory write failure prevents the orchestrator call;
- existing V2, campaign, and hardware tests remain green.

## Out of scope

- Dashboard controls or a new HTTP endpoint;
- online model training or reinforcement learning;
- vector databases, embeddings, or semantic retrieval;
- changing safety ranges or enabling real hardware;
- FIR candidates;
- storing API keys or raw base64 payloads.
